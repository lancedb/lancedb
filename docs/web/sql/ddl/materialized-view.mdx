A materialized view stores a query's result as rows, kept current by a refresh.
It is the counterpart to a [view](/sql/ddl/view), which stores only the query.

<Note>
Materialized views are off by default in LanceDB Enterprise and have to be enabled
there. Which statements and query shapes a deployment accepts, whether it needs
the source table to have stable row ids, and how it refreshes a view depend on
its LanceDB Enterprise version and configuration.
</Note>

## CREATE MATERIALIZED VIEW {#create}

<CodeGroup>
```sql SQL icon="database"
CREATE MATERIALIZED VIEW <name> AS SELECT ...
```
</CodeGroup>

Once created, a materialized view can be queried like a table. Use the
statements below to list, refresh and drop it. For SDK methods, see
[Materialized views](/management/materialized-view#create).

## SHOW MATERIALIZED VIEWS {#show}

```sql
SHOW MATERIALIZED VIEWS IN analytics.`team$ml` LIMIT 100;
SHOW MATERIALIZED VIEWS IN analytics.`team$ml` LIMIT 100 FROM '<page-token>';
```

Returns two non-null string columns: `namespace_path`, a compact JSON array
of parent namespace components (`[]` for root), and `name`, the unqualified
object name. Omitting `IN` lists all authorized namespaces in the current database;
`IN team$ml` selects that exact path without a database qualifier; `IN public` selects
the current database's root. Listings require the relevant database and
namespace `USAGE` privileges.

The listing contains identifiers; use `DESCRIBE MATERIALIZED VIEW` for its defining query and refresh metadata.

Page through results using `LIMIT n [FROM '<page-token>']`. Read the opaque
`lancedb.next_page_token` from the Arrow result schema metadata and pass it back
unchanged with the same object type and scope. Stop when no token is returned;
a short or empty page can still carry a continuation. See
[catalog listing pagination](/sql/pagination).

## Refreshing one {#refresh}

<CodeGroup>
```sql SQL icon="database"
REFRESH MATERIALIZED VIEW chunks
```
</CodeGroup>

See [REFRESH MATERIALIZED VIEW](/sql/dml/refresh-materialized-view) for the full syntax,
and compatibility notes for older server versions.

## ALTER MATERIALIZED VIEW {#alter}

```sql
ALTER MATERIALIZED VIEW frames_captioned SET auto_refresh_enabled = true;
ALTER MATERIALIZED VIEW frames_captioned SET auto_refresh_interval_seconds = 300;
ALTER MATERIALIZED VIEW frames_captioned SET auto_refresh_enabled = false;
```

The whole view toggles together; there is no per-output granularity the way
a multi-output Function column has one setting per output. SET takes effect
immediately and does not itself run a refresh:

- **Disabling** prevents new automatic refreshes. An inflight one may still
  finish, and `REFRESH MATERIALIZED VIEW` keeps working manually.
- **Re-enabling catches up the entire backlog in one pass**, the same as a
  computed column's [automatic refresh](/sql/ddl/table#automatic-refresh-options):
  the next scheduler tick picks up every source change accumulated since the
  view was disabled, immediately, with no further write needed to trigger it.

A materialized view's *initial* population, at `CREATE` or when the server
runs it, happens regardless of `auto_refresh_enabled`; only refreshes after
that are gated by the setting.
*/}

## Dropping one {#drop}

```sql
DROP MATERIALIZED VIEW <name>
```

A dedicated statement; the SDKs emit it rather than
[`DROP TABLE`](/sql/ddl/table#drop), even though a materialized view **is**
a table underneath. For the same reason, dropping one removes stored rows,
unlike dropping a [view](/sql/ddl/view#drop).

<Note>
**Enterprise job type for a refresh:** `sql`. Dropping, by contrast, runs the
same underlying job as dropping any table, `drop_table` or `drop_object`.
</Note>
