Refresh a [materialized view](/feature-engineering/materialized-views) to
bring its stored rows up to date after the source table changes.

<Note>
In SQL this is [`REFRESH MATERIALIZED VIEW`](/sql/dml/refresh-materialized-view).
</Note>

## Refresh a view {#refresh}

<CodeGroup>
```python Python icon="python"
view.refresh()
```
</CodeGroup>

Every refresh rebuilds the view completely from its source query -- there is
no incremental refresh. Calling it again with no source changes still
rebuilds and commits a new table version.

The result reports what the refresh did:

<CodeGroup>
```python Python icon="python"
result = view.refresh()
result.rows_written  # rows in the rebuilt view
result.source_version  # the source table version the view now reflects
result.version  # the view's own new table version
```
</CodeGroup>

Pass `source_version=N` to refresh against a particular source version
instead of the latest:

<CodeGroup>
```python Python icon="python"
view.refresh(source_version=12)
```
</CodeGroup>

Use `view.table.count_rows()` for the view's row count at any time; it
always matches `rows_written` from the most recent refresh.

## Automatic refresh {#auto-refresh}

Set scheduling options when [creating the view](/feature-engineering/materialized-views#auto-refresh):

<CodeGroup>
```python Python icon="python"
view = db.create_materialized_view(
    "frames_captioned",
    source="frames",
    select=["frame_id", "video_id", "ts", "caption"],
    where="selected = true",
    auto_refresh_enabled=True,
    auto_refresh_interval_seconds=300,
)
```
</CodeGroup>

`auto_refresh_interval_seconds` is a positive minimum delay after the last
successful refresh before the next automatic one is eligible; omit it to let
the server decide. The whole view toggles together -- there is no
per-column granularity the way a computed column has one setting per output.

The view's *initial* population, at creation or when the server first runs
it, happens regardless of these settings; only refreshes after that are
gated. Manual `view.refresh()` keeps working whether or not automatic
refresh is enabled.

## When a refresh fails {#failures}

A refresh replaces the view's stored rows in one commit, so a failure leaves
the view as it was after its last successful refresh. Fix the cause and
refresh again.
