A catalog is what LanceDB knows about. Everything you create lives in one and is
addressed through it — the objects below, arranged in a hierarchy.

This section covers what each object is and the basic operations on it. Where an
object has depth — how to search a table, how to refresh a view — the page links
to the section that covers it rather than repeating it.

## The objects {#objects}

| Object | What it is |
| --- | --- |
| [Database](/catalog/database) | The root. A connection opens one. |
| [Namespace](/namespaces) | A named grouping of tables inside a database. |
| [Table](/tables) | Rows and columns, versioned. The thing most operations act on. |
| [Materialized view](/feature-engineering/materialized-views) | A table whose contents come from a query, computed and stored. |
| [View](/catalog/view) | A saved query. Computed when read, not stored. |
| [Function](/feature-engineering/functions) | Registered code, applied to produce column values. |

## How they nest {#hierarchy}

```
database
└── namespace
    ├── table
    ├── materialized view      (a table, defined by a query)
    ├── view                   (a query, not stored)
    └── function
```

A namespace can contain further namespaces, so the hierarchy is as deep as your
organisation needs. A table is reached by its path through that hierarchy.

## Views and materialized views are different objects {#views}

The names are close enough to mislead. Both are defined by a query over other
tables; the difference is when that query runs.

- A **materialized view** stores its rows. A refresh computes them, and reads
  are reads of stored data — fast, and as current as the last refresh.
- A **view** stores only the query. Every read runs it, so a view is never stale
  and never faster than the query it wraps.

Reach for a materialized view when the query is expensive and the data changes
less often than it is read. Reach for a view when correctness matters more than
latency, or when the query is cheap.

## What is not here {#elsewhere}

Indexes belong to a table but are covered under [Maintenance](/indexing),
because creating one is a decision about performance rather than about
structure.
