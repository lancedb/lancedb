A **Secret** is a catalog object, like a table or a namespace: a named
credential, such as a model provider's API key, stored once and addressed by
name. A [Function](/curation/create-function) binds a Secret by reference
when you register it, never by value; see
[Vend a Secret to a Function](/curation/vend-secret) for how that binding
reaches running code.

The design rule is **bind by reference, resolve late**. A Function records
*which* Secret it reads, never the value, and the value is looked up each
time a job starts. That is what lets a credential be rotated or revoked
without touching the Functions, columns or tables that use it.

## Create and manage {#manage}

Every call takes an optional `namespace_path`; the default is the root
namespace.

<CodeGroup>

```python Python
db.create_secret("openai-prod", value, namespace_path=["platform"])

db.alter_secret("openai-prod", new_value, namespace_path=["platform"])

for name in db.list_secrets(namespace_path=["platform"]):
    print(name)

info = db.describe_secret("openai-prod", namespace_path=["platform"])
info.created_at_millis, info.updated_at_millis

db.drop_secret("openai-prod", namespace_path=["platform"])
```

```sql SQL
CREATE SECRET platform.`openai-prod` WITH (value = 'sk-...');

ALTER SECRET platform.`openai-prod` SET WITH (value = 'sk-...');

SHOW SECRETS IN platform;

DESCRIBE SECRET platform.`openai-prod`;

DROP SECRET platform.`openai-prod`;
```

```bash REST
# Create. The Secret identifier is its namespace path and name joined by `$`.
curl -X POST "$LANCEDB_HOST_OVERRIDE/v1/secret/platform\$openai-prod/create" \
   -H "Content-Type: application/json" \
   -H "x-api-key: $LANCEDB_API_KEY" \
   -H "x-lancedb-database: $LANCEDB_DATABASE" \
   -d '{"value": "sk-..."}'

# List the names in one namespace.
curl -X GET "$LANCEDB_HOST_OVERRIDE/v1/namespace/platform/secret/list" \
   -H "x-api-key: $LANCEDB_API_KEY" \
   -H "x-lancedb-database: $LANCEDB_DATABASE"
```

</CodeGroup>

| Operation | REST | Returns |
| --- | --- | --- |
| Create | `POST /v1/secret/{id}/create`, body `{"value": ...}` | Nothing. Fails if the name is taken, so a create never silently becomes a rotation. |
| Rotate | `POST /v1/secret/{id}/alter`, body `{"value": ...}` | Nothing. Fails if the Secret does not exist. |
| Describe | `POST /v1/secret/{id}/describe` | `name`, `created_at_millis`, `updated_at_millis`, and `history` |
| List | `GET /v1/namespace/{id}/secret/list` | Names, paginated by `limit` and `page_token`. The root namespace is `$`. |
| Drop | `POST /v1/secret/{id}/drop` | `{"dropped": bool}`. Dropping a Secret that is already gone returns `false`, not an error. |

A Secret's value is never returned by any of these calls, in either
direction: `create` and `alter` take it as input and return nothing, and
`describe` reports only metadata. See the
[SQL reference](/sql/ddl/secret) for the same operations' SQL syntax and
result rows.

<Note>
SQL has no syntax for binding a Secret to a Function. Register Functions that
bind Secrets through the Python SDK or REST; see
[Vend a Secret to a Function](/curation/vend-secret).
</Note>

## Properties and guarantees {#security}

LanceDB guarantees that:

- No API returns a Secret's value.
- Values do not appear in Function source, Function versions, jobs, logs, or
  error messages. Errors raised by Function code are redacted, within
  [limits](#redaction).
- A Function receives only the Secrets bound to it.
- Values are always [encrypted at rest](#encryption).

Redaction is a safety net, not a boundary: Function code that logs, returns
or sends a credential will leak it.

### Encryption at rest {#encryption}

Every Secret is encrypted with your deployment's key in AWS KMS, Google Cloud
KMS, or Azure Key Vault, so storage, backups and replicas hold only
ciphertext. Decryption goes through your KMS, which records it in your
cloud's audit log. A deployment without a KMS key does not offer Secrets;
see [KMS integration](/enterprise/deployment/kms).

<Badge color="blue">BYOC</Badge> You are responsible for the network egress
policy for the jobs that run Functions, and for scoping the Function
identity's cloud role to the KMS key so it can decrypt but not encrypt.

### Redaction {#redaction}

If a Function raises an error or skips a row with a message that contains a
bound value, LanceDB replaces each exact occurrence with `[REDACTED]` before
the message is recorded. Redaction matches only the exact value: a value
that is base64-encoded, sliced, or otherwise transformed is not caught.
Function code that prints a credential, writes it into a column, or sends
it elsewhere will leak it, so review a Function bound to a Secret as code
that holds that credential.

## Limits {#limits}

| Item | Limit |
| --- | --- |
| Secret name | 1--128 characters from `A-Z a-z 0-9 _ . -`. `$` is reserved as the namespace delimiter. |
| Value | One string, at most 64 KiB |
| Bindings per Function | 16 |
| Environment variable name | `[A-Za-z_][A-Za-z0-9_]*`, and not [reserved](#reserved) |
| Variables per Function | Each bound once. Two variables may bind the same Secret. |
| `describe` history | The most recent 100 alterations |

### Reserved variables {#reserved}

A Secret cannot be bound to a variable that LanceDB sets for Functions
itself. These names are reserved:

- Exact names: `HOME`, `PATH`, `TEMP`, `TMP`, `TMPDIR`, `LANG`, `LC_ALL`,
  `LC_CTYPE`, `TZ`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` (and their
  lowercase forms), `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`,
  `UV_CACHE_DIR`, `UV_NATIVE_TLS`, `UV_PYTHON_INSTALL_DIR`, `RUST_BACKTRACE`
- Prefixes: `DYLD_`, `LANCE_`, `LANCEDB_`, `LD_`, `PYTHON`, and a few others
  LanceDB reserves for its own use. `create_function` refuses a reserved
  name and says which one.

## Troubleshooting {#troubleshooting}

**`Secret 'X', bound to VAR, does not exist`** when adding a column or
refreshing one: the Secret was never created in that namespace, was dropped,
or its name is misspelled in the binding. Create it, or register a new
Function version with the right name.

**501 from a Secret route**: the deployment has no KMS key configured, so
Secrets are disabled. See [KMS integration](/enterprise/deployment/kms).

## Privileges {#privileges}

A Secret is its own object in the [authorization](/governance/privileges)
model, a namespace child like a table, so a grant names one credential
rather than a whole database.

| Operation | Requires |
| --- | --- |
| Create a Secret | `CREATE_SECRET` on the namespace. The creator owns the new Secret. |
| Rotate (`alter`) | `UPDATE` on the Secret |
| Describe | `USAGE` on the Secret |
| List | `USAGE` on the database and the namespace |
| Drop | `OWNERSHIP` on the Secret. Dropping also deletes its grants. |
| Bind it to a Function | `USAGE` on the Secret |

`UPDATE` is deliberately separate from `USAGE`, so a rotation service can
replace a value without being able to bind the Secret to a Function of its
own. See [Privileges](/governance/privileges#sql) for how to grant these
privileges, and [GRANT and REVOKE](/sql/ddl/secret#grant) for the full SQL
statement syntax.
