## What does consistency mean here? {#consistency}

A table read uses a consistent snapshot of the data. **Freshness** describes how
recent that snapshot is. A reader can see a coherent earlier version while
another process has already committed newer data.

For example, a dashboard may need the latest updates, while an experiment may
need to keep reading a specific table version. These are different requirements.

## When do changes become visible? {#visibility}

In **OSS**, a table handle sees its own committed writes. By default, it does
not automatically check for changes made through other handles or processes.
Use a read consistency interval or `checkout_latest()` to pick up those changes.

In **Enterprise**, readers use the service's configured freshness policy.
A connection can request fresher data. When a read must include a completed
write, use a zero interval or call `checkout_latest()` after the write, with a
client and server that support these freshness controls.

## How do you control freshness? {#configure-consistency-parameters}

Set `read_consistency_interval` when connecting. The setting applies to reads;
it does not change the transaction boundary of a write.

| Setting | OSS | Enterprise |
| --- | --- | --- |
| **Unset** | Keep the open table version until explicitly refreshed or changed by that handle. | Use the service's configured freshness policy. |
| **Zero** | Check for the latest committed version on every read. | Request the latest committed version on every read. |
| **Non-zero interval** | Check for updates on a read once the interval since the last check has elapsed. | Request data no older than the interval allows; the service may return fresher data. |

`checkout_latest()` explicitly refreshes an OSS table handle. On Enterprise it
asks subsequent reads on that handle to reflect data at least as recent as the
refresh request. To read a fixed historical version instead, use
[table versioning](/management/table#versioning).

## How should you choose? {#choosing}

- **Reads that must include recent writes:** use a zero interval. Checking more
  frequently can increase read latency and storage requests.
- **Dashboards with an acceptable delay:** choose an interval within that delay
  budget, then measure the effect on latency and cost.
- **Reproducible experiments:** read an explicit table version and retain it for
  as long as the experiment needs it.

There is no single interval that suits every application. Choose based on how
stale a result your users can accept.
