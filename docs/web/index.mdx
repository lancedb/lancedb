**LanceDB** is a [multimodal lakehouse](https://lancedb.com/blog/multimodal-lakehouse/) for AI teams that need
one data layer for curation, feature engineering, search and retrieval, and model training.
It is built on top of [Lance](/basics/lance), an open-source lakehouse format designed for multimodal AI data.

Move from data exploration to model training on one, unified platform without needing to manage a
fragmented stack of storage, feature, retrieval, and training systems.

## Build better models, faster {#build-better-models-faster}

Training data and experimentation slow down when raw data, metadata, embeddings, features, and governance
artifacts live in separate systems. LanceDB keeps them together in one versioned multimodal table, so AI teams spend less
time stitching infrastructure together and more time improving datasets, testing features, and keeping GPUs fed.

<Steps>
  <Step title="One table for the whole AI data loop">
    Store images, video, audio, text, annotations, embeddings, and model-generated features together in one schema-enforced table.
    The same table can support dataset curation, feature backfills, experiment splits, retrieval, and training.
  </Step>
  <Step title="High-throughput data access for training">
    Training workloads mix fast random access with high-throughput sequential scans. LanceDB is designed for both, so
    teams can shuffle data into GPU-ready batches more efficiently, improve input throughput, and iterate on experiments faster.
  </Step>
  <Step title="Fast, versatile search and retrieval">
    Whether the end user is a human or an agent, LanceDB powers production retrieval workloads such as semantic search,
    hybrid search, RAG, agent memory, and recommendation systems. Retrieval runs against the same LanceDB tables used
    for curation, feature engineering, and training workflows.
  </Step>
</Steps>

Use the same table to curate training data, add derived features, retrieve examples, and feed training jobs that rely on expensive GPUs.
Training workloads can sample, shuffle, and scan projected columns from local storage or object storage, then assemble
GPU-ready batches from a tagged dataset version. Training pipelines need curation, derived features, reproducible
splits, fast random access, and a clean path into frameworks such as PyTorch -- LanceDB keeps all of it connected
through the same table model, whether a workflow uses one table or several related ones.

## Architecture {#architecture}

LanceDB Embedded and Enterprise are both built on [Lance](/basics/lance), which stores table data, versions, and
indexes in open, columnar files. The format and table model are the same across both offerings -- what changes is
how storage and compute are organized around them.

```mermaid
flowchart TB
    subgraph Embedded["LanceDB Embedded"]
        EmbApp(["Your application"])
    end

    subgraph Enterprise["LanceDB Enterprise"]
        EntSdk(["LanceDB SDK"]) --> EntSvc{{"Query serving, caching, indexing"}}
    end

    Lance[("Lance format<br/>table data, versions, indexes")]

    Embedded --> Lance
    Enterprise --> Lance
```

Embedded reads and writes tables on local disk or in object storage from inside your application process.
Enterprise keeps durable table data and index artifacts in object storage, independently of the machines serving
requests, and separates query serving, read execution and caching, and indexing and background work into their
own independently sized components. Caches accelerate reads; they are never the durable source of truth. Here is
how Enterprise organizes those components internally:

```mermaid
flowchart TB
    Clients(["Clients"])
    QueryFleet{{"Query Fleet<br/>query serving"}}
    ExecutorRing{{"Executor Ring<br/>read execution + cache"}}
    Indexer{{"Indexer<br/>background work"}}
    EventQueue[["Event Queue"]]
    Storage[("Cloud Object Storage")]

    Clients --> QueryFleet
    QueryFleet -- reads --> ExecutorRing
    QueryFleet -- writes --> Storage
    QueryFleet -- change events --> EventQueue
    EventQueue --> Indexer
    ExecutorRing -- reads --> Storage
    Indexer -- writes --> Storage
```

Sharing a format does not mean an Enterprise deployment automatically opens an existing Embedded database --
plan how to move or connect your data and configure access for your deployment.

## Embedded and Enterprise {#embedded-and-enterprise}

LanceDB ships as two offerings on the same Lance format and table model. Start locally with Embedded, then move to
Enterprise when your team needs distributed scale, managed infrastructure, private deployment, or higher-throughput
curation, feature engineering, search and retrieval, and training workflows.

### 1\. LanceDB Embedded {#1-lancedb-oss}

**LanceDB Embedded** is an open-source, embedded retrieval library, with client SDKs in Python, TypeScript and
Rust -- the application itself plans queries, builds indexes, and runs background work, with no separate database
server to deploy. This fits local retrieval applications, notebooks, development, and single-node data pipelines,
where your application controls its own compute resources and [table maintenance](/maintenance/compaction).

### 2\. LanceDB Enterprise {#2-lancedb-enterprise}

[LanceDB Enterprise](/enterprise) is a petabyte-scale (and beyond), distributed **multimodal lakehouse** platform
built for search, curation, feature engineering, and high-throughput training data access workflows on top of the
same core table abstraction, without building bespoke infrastructure. Applications connect through a LanceDB SDK
while the service handles requests across a fleet, with query serving, read execution and caching, and indexing
and background work sized and scaled as separate components. Read the
[Enterprise architecture](/enterprise/architecture) for the component details and request flows.

Teams choose Enterprise to:

- **Serve growing workloads** -- add query-serving capacity and let Enterprise cache frequently read table data near
  compute as traffic grows.
- **Reduce operational work** -- let the service handle background [compaction](/maintenance/compaction) and
  [cleanup](/maintenance/cleanup) instead of scheduling them in application code.
- **Fit deployment requirements** -- run a managed deployment or bring LanceDB into your own cloud account, with
  OpenTelemetry metrics and traces.
- **Connect data workflows** -- use the same tables for retrieval, curation, and training data access, with
  [SQL](/basics/sql), [feature engineering](/feature-engineering), and [Geneva](/geneva) feature backfills.

To set up LanceDB Enterprise in your organization, [reach out to us](https://www.lancedb.com/contact).
