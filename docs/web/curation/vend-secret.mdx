A Function that calls an external service needs a credential without
putting it in the function's source -- see
[Create a Function](/curation/create-function#remote) for how to register
one. A [Secret](/management/secret) is a database-scoped named credential:
you create it once, then bind it *by reference* -- by name, not by value --
when you register the Function that needs it.

## Specify the Secret when you register the Function {#specify}

Store the credential, then bind it to an environment variable the function's
code already reads:

<CodeGroup>
```python Python icon="python"
import os
from lancedb import EnvVarSecret, udf

db.create_secret("openai-prod", os.environ["OPENAI_API_KEY"])

@udf
class embed_remote:
    def __init__(self, model: str = "text-embedding-3-small"):
        import os
        from openai import OpenAI

        self.client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
        self.model = model

    def __call__(self, text: str) -> list[float]:
        response = self.client.embeddings.create(input=text, model=self.model)
        return response.data[0].embedding

version = db.create_function_async(
    embed_remote,
    secrets=[EnvVarSecret(secret_name="openai-prod", env_variable="OPENAI_API_KEY")],
).wait()
```
</CodeGroup>

The function's own code never names the Secret -- it reads
`OPENAI_API_KEY` the same way it would outside LanceDB. The binding, in
`secrets=[...]`, is what connects that variable to the stored credential.
It is checked for shape at registration (valid variable name, not reserved,
not repeated) but not resolved yet: the Secret does not have to exist until
a column actually uses this Function version, so you can create the
Function and its Secret in either order.

## How the value reaches a running evaluation {#delivery}

The Secret's value is looked up fresh each time work starts, never read
once and cached in the Function's definition:

| Step | What happens |
| --- | --- |
| `add_columns` with this Function version | Every bound Secret must now exist. The column pins this exact version, not a value. |
| A refresh starts -- `refresh_column`, or a materialized view's refresh | Every bound Secret must still exist, checked before any row is computed. |
| The refresh actually runs | LanceDB looks up each bound Secret's current value and sets it as that environment variable, for that evaluation only. No other environment variable carries over. |

This is why rotating a Secret needs no new Function version and no column
change: `alter_secret` changes the value a *future* lookup returns, and
every lookup after that point gets it, even inside a refresh that is already
running -- rows or batches it has not reached yet pick up the new value,
while rows it already computed keep the old one.

### Rotate and revoke {#rotation}

`alter_secret` and `drop_secret` never interrupt work in progress, so a
routine rotation cannot fail a backfill halfway through:

| Action | Running jobs | Next job | New Function version? |
| --- | --- | --- | --- |
| `alter_secret` | Work in progress keeps its value; work started afterwards gets the latest value | Uses the latest value | No |
| `drop_secret` | Run to completion on the last value | Refused, naming the Secret | No |
| Revoke the key at its provider | Fails on their next call to the provider | Fails until a new value is set | No |
| Re-create a dropped name | Keeps the dropped Secret's last value | Picks up the new Secret | No |

Because a rotation creates no new Function version, it also reaches columns
pinned to a version registered before it. Binding a Function to a
*different* Secret or variable does register a new version, and existing
columns keep the binding they were declared with.

<Warning>
To stop a credential from being used **now**, revoke it at its provider,
for example by deleting the key in the OpenAI console. A value already
handed to a running job cannot be recalled.
</Warning>

`drop_secret` cannot be undone, and it does not check for Functions still
bound to the Secret.

<Note>
Reading a column this Function already filled needs only `SELECT` on the
table. No Function runs on the read path, so a reader needs no grant on the
Function or its Secrets -- only someone triggering a refresh does.
</Note>

## Vending during SQL evaluation specifically {#sql}

A computed column's expression and a `CREATE MATERIALIZED VIEW` query both
plan and execute as SQL, so a Function called from either one is vended its
Secrets the same way: at the evaluation that fills the column or refreshes
the view, not at declaration time.

<CodeGroup>
```sql SQL icon="database"
CREATE MATERIALIZED VIEW frames_captioned AS
SELECT f.frame_id, caption(f.jpeg) AS caption
FROM frames f
```
</CodeGroup>

`caption` here is a Function bound to a Secret through the Python SDK or
REST when it was registered -- SQL has no syntax for the binding itself, only
for calling the already-registered Function. The `CREATE MATERIALIZED VIEW`
statement's initial population, and every `REFRESH MATERIALIZED VIEW`
after it, each look up the bound Secret's current value independently.

## Troubleshooting {#troubleshooting}

**403 when adding or refreshing a Function column**: you need `USAGE` on
the Function *and* on every Secret it binds, in addition to the table
privilege. The error names the object you are missing.

**The Function runs but its provider rejects the key**: a misspelled
*environment variable* cannot be caught at registration, because nothing
knows which variables a Function reads. Check that `env_variable` matches
what the library expects, for example `OPENAI_API_KEY`.
