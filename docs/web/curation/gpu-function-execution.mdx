[Registering a GPU Function](/curation/create-function#gpu) sets `gpu=True`
and an optional `gpu_class`; this page covers what happens after that, when
a job actually needs a worker. An operator configures one or more named
**GPU classes** for the deployment -- each one a Kubernetes node selector,
toleration set, and resource name (such as `nvidia.com/gpu`) pointing at a
specific pool of GPU nodes, plus a hardware description (GPU model, GPU
memory, how many GPUs one worker may request). A Function with no
`gpu_class` uses the deployment's `default` class.

## Placement {#placement}

When a job needs to run a GPU Function, the agent resolves its `gpu_class`
(or `default`) to that class's node selector, tolerations, and resource
name, and requests a worker pod shaped accordingly -- this is a separate
placement path from the ordinary CPU worker ladder used by non-GPU
Functions and other background jobs (see
the [Job Framework](/basics/jobs) for that general job
machinery). The resulting pod can only schedule onto a node matching the
class's selector and tolerations, so a class is really naming a pool of
nodes, not just a resource count.

## Waiting for capacity {#capacity}

A GPU class describes the deployment's hardware, not live availability --
listing classes never tells you whether a GPU is free right now. If no
node in the class has room, the worker pod stays pending rather than
failing the job outright or falling back to a CPU worker: the job reports
that it is waiting on that GPU class's capacity, and starts running as soon
as a matching node has room. A job stuck waiting indefinitely usually means
the class's node pool needs more capacity, not that anything is
misconfigured.

