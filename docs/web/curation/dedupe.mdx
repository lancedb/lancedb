[Ranking](/curation/windowing#dedup) removes records by an
explicit rule, such as keeping the latest version of a known key. This page
covers the other kind of duplicate: records with no shared key that are still
nearly identical, judged by distance between their embeddings -- a stopped
camera holding one pose for a few seconds, or two scraped pages with the same
paragraph reworded. `dedupe` and `duplicate_pairs` find these directly over a
vector index, without a pairwise scan.

## Example data {#example-data}

Connect with an [Enterprise connection](/basics/catalog#enterprise). A small
fixture keeps the distances easy to check by hand.

<Accordion title="Create the example table">

`curation_embeddings` has eight records. Rows 10 and 20 are near-identical;
rows 30, 40 and 50 form one looser cluster; the rest are distinct.

<CodeGroup>
```python Python icon="python"
import pyarrow as pa
from lancedb.index import IvfFlat

schema = pa.schema([
    pa.field("id", pa.int64(), nullable=False),
    pa.field("caption", pa.utf8()),
    pa.field("embedding", pa.list_(pa.float32(), 2)),
])
table = db.create_table("curation_embeddings", [
    {"id": 10, "caption": "a cat on a chair",     "embedding": [0.0, 0.0]},
    {"id": 20, "caption": "a cat on the chair",    "embedding": [0.0, 0.03]},
    {"id": 30, "caption": "a dog in a field",      "embedding": [5.0, 5.0]},
    {"id": 40, "caption": "a dog in the field",    "embedding": [5.0, 5.05]},
    {"id": 50, "caption": "a dog out in a field",  "embedding": [5.0, 5.10]},
    {"id": 60, "caption": "a bird in a tree",      "embedding": [10.0, 10.0]},
    {"id": 70, "caption": "a boat on the water",   "embedding": [20.0, 20.0]},
    {"id": 80, "caption": "a car on the road",     "embedding": [30.0, 30.0]},
], schema=schema)

table.create_index("embedding", config=IvfFlat(num_partitions=1, distance_type="l2"))
table.wait_for_index(["embedding_idx"])
```
</CodeGroup>

`dedupe` and `duplicate_pairs` read the vector index, so the column needs one
before either function runs; a query against unindexed fragments is rejected
rather than silently returning stale or wrong results.

For an `l2` index, `distance_threshold` and the `distance` column below are
both **squared** L2, not the plain L2 a plain SQL `distance()` call returns.

</Accordion>

## Collapse near-duplicates {#dedupe}

`dedupe` returns one representative row per cluster of records within
`distance_threshold` of each other -- rows 10/20 collapse to one, 30/40/50
collapse to one, and the three distinct rows pass through unchanged, leaving
ids 10, 30, 60, 70 and 80:

<CodeGroup>
```sql SQL icon="database"
SELECT id, caption
FROM dedupe(
    'curation_embeddings',
    'embedding',
    distance_threshold => 0.003
)
ORDER BY id
```
</CodeGroup>

Every other column survives unchanged, since `dedupe` returns full rows, not
just which ones matched. Clustering is transitive: 30 and 40 are within
`distance_threshold` of each other, and so are 40 and 50, so all three
collapse into one representative even though 30 and 50 alone sit outside the
threshold. Pass `resolution => 'direct_representative'`
for a simpler, non-transitive selection instead, if a chained cluster like that
should not merge into one representative.

Which row survives as the representative is not guaranteed to stay the same
across appends: a later row that bridges two previously separate clusters can
change which id represents the merged cluster. Do not treat a representative's
id as a stable identifier for its cluster.

## Inspect the pairs instead {#pairs}

`duplicate_pairs` returns the matching edges themselves, without collapsing
anything -- useful for review, or for a threshold that is still being tuned:

<CodeGroup>
```sql SQL icon="database"
SELECT id_a, id_b, distance
FROM duplicate_pairs(
    'curation_embeddings',
    'embedding',
    distance_threshold => 0.003,
    id_column => 'id'
)
ORDER BY id_a
```
</CodeGroup>

This returns the pairs `(10, 20)`, `(30, 40)` and `(40, 50)` -- note 30 and 50
are not a direct pair here (their squared L2 distance is `0.01`, outside the threshold),
even though `dedupe` merges all three transitively above.

## Keep it current with a materialized view {#materialized}

Wrap either call in a [materialized view](/management/materialized-view) so
the deduplicated set stays current as new records arrive, instead of
recomputing it from scratch on every curation pass:

<CodeGroup>
```sql SQL icon="database"
CREATE MATERIALIZED VIEW curation_embeddings_deduped AS
SELECT * FROM dedupe(
    'curation_embeddings',
    'embedding',
    distance_threshold => 0.003
)
```
</CodeGroup>

See [Refresh a materialized view](/feature-engineering/refresh-materialized-view)
for manual and automatic refresh options to keep it current as new records land.

## Index, snapshot and recall limits {#limits}

These are Enterprise SQL table functions, not standard SQL or a registered
Python Function. They require one compatible current vector index covering
the scanned snapshot. Wait for indexing to finish after ingestion and inspect
index coverage before running a full scan. Unindexed fragments are rejected;
deleted rows are excluded at the pinned dataset version.

The scan compares candidates **within each physical IVF partition and index
segment**. It does not compare across partitions or segments. Scanning every
partition therefore does not establish global all-pairs recall. Quantized
indexes compare their encoded vector representations; `IVF_FLAT` compares the
stored vectors. Thresholds must match the index's metric: L2 is squared L2,
cosine is `1 - cosine`, dot distance is `1 - dot`, and Hamming counts differing
bits. Inspect close examples and known duplicates before choosing a threshold.

`duplicate_pairs` reports `dataset_version`, `segment_id` and `partition_id`.
Retain those with the index configuration and source version when comparing
runs. Pass `id_column` for application IDs, rather than treating physical row
addresses as durable identifiers. A new append, index change or bridge between
components can change groups and representatives.

## Efficient use and scale qualification {#production}

Start with [`duplicate_pairs` partition sampling](/sql/dql/duplicate-pairs#sampling),
using a recorded seed and a bounded partition count. Inspect pair density and
threshold quality before running `dedupe`, which always scans every partition.
Sampling partitions is not uniform row sampling and can miss rare groups.
`resolution='connected_components'` merges transitive chains;
`direct_representative` uses direct representative relationships instead.

Pair work grows quadratically within dense partitions, and a loose threshold
can emit a quadratic number of edges. An outer `LIMIT` is not a resource
budget for upstream pair finding or group resolution. Avoid repeatedly
materializing all pairs in a Python list; select needed columns, aggregate on
the server, and persist a reviewed result when repeated reads justify it.
Measure peak memory, spill storage, elapsed time and pair count on
representative partitions before increasing scope.

The [LeRobotDataset integration](/integrations/lerobotdataset) illustrates a
27.6-million-row data workflow. Its timings are not a versioned qualification
of this deduplication path on arbitrary indexes or hardware. A 10-billion-row
run is not qualified by that example. Qualify source/index versions, partition
sizes, metric, threshold, worker resources, spill limits and correctness on your
deployment before extrapolating. There is no universal row-count or latency
guarantee in this guide.

For text shingles and MinHash signatures, use the distinct
[MinHash workflow](/enterprise/sql-minhash). Vector distance deduplication and
MinHash/Jaccard text deduplication have different indexes and thresholds.

Agents can follow the repository's
[vector deduplication skill](https://github.com/lancedb/lancedb/blob/main/.agents/skills/lancedb-vector-dedup/SKILL.md)
to apply these checks without inventing Function options or scale guarantees.
