LanceDB supports vector, full-text and hybrid search. Use vector search to find
similar content, full-text search to match words, or hybrid search to combine
both. Filters narrow the results to records that match your criteria.

## Choose a search method

| You want to find | Use | Prepare |
|:----------------|:----|:--------|
| Items similar to a query, such as related passages or images | [Vector search](/search/vector-search) | Stored vectors and a compatible query vector |
| Documents represented by several embeddings | [Multivector search](/search/vector-search#multivector) | A multivector column and compatible query vectors |
| Records containing particular words or phrases | [Full-text search](/search/full-text-search) | An FTS index on the text column |
| Relevant meaning alongside keyword matches | [Hybrid search](/search/hybrid-search) | Vectors and an FTS index |
| Rows matching a condition, without similarity ranking | [Filtering](/search/filtering) | A predicate over table columns |

Vector search can run without an index. An approximate nearest-neighbor index
reduces the work needed for larger tables, with a tradeoff between recall and
latency. Full-text search needs an FTS index before you query it.

## Before you search {#before-you-search}

For vector search, generate stored and query vectors with the same embedding
model and compatible settings. Their dimensions must match. Keep the fields
you want to return, such as document text or an item ID, in the same table.

For full-text search, choose the text column and build its index. Enterprise
builds indexes in the background, so wait for the index to be ready before
querying it. Phrase queries also need token positions in the index. See
[FTS indexes](/indexing/fts-index).

## Read the results

Use `select()` to choose the columns your application needs and `limit()` to
set the maximum number of results. The search also returns a ranking value:

| Search method | Ranking column | Order |
|:--------------|:---------------|:------|
| Vector | `_distance` | Smaller distance first |
| Full-text | `_score` | Higher text relevance first |
| Hybrid | `_relevance_score` | Higher combined relevance first |

These values have different meanings. Do not compare a vector distance directly
with a full-text score or treat a reranker score as a probability.

## Add filters and reranking {#performance}

[Filters](/search/filtering) restrict which rows qualify, such as documents
from a particular collection. Prefiltering searches within those rows.
Postfiltering removes nonmatching rows from the candidates already retrieved,
so it can leave fewer results than requested.

[Reranking](/reranking) reorders the candidates returned by retrieval. Start
with representative queries and expected results, then compare changes to
relevance and latency. A reranker cannot recover a relevant row that retrieval
never returned.

## Read large result sets in batches {#avoid-materializing-the-whole-table}

Materializing all rows at once can exhaust application memory. For exports and
training reads, use bounded queries or the batch-reading interfaces described
in [Data loading](/training/data-loading). The SDK buffers Enterprise
query responses before exposing batches. Set a query limit rather than relying
on batch iteration alone to bound memory.

Direct Lance dataset access through Python's `table.to_lance()` is an OSS
interface. Use the SDK query builders for reads that need to work with both
OSS and Enterprise.

## Investigate a slow query {#diagnostics}

Use [query plans](/search/explain) to see the scans, filters and indexes selected
for a query. `explain_plan()` inspects the plan; `analyze_plan()` executes the
query and reports measurements. Compare one change at a time, such as adding
an index, returning fewer columns, or adjusting search parameters.
