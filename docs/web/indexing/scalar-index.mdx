Scalar indexes accelerate filters on values such as numbers, categories and
strings. Use them for selective table queries or metadata filters combined
with vector and full-text search.

LanceDB supports these scalar index types, among others:

- `BTREE`: Stores column data in sorted order for binary search. Best for columns with many unique values.
- `BITMAP`: Uses bitmaps to track value presence. Ideal for columns with few unique values (e.g., categories, tags).
- `LABEL_LIST`: Special index for `List<T>` and `LargeList<T>` columns of primitive values supporting `array_contains_all` and `array_contains_any` queries.
- `FM`: FM-Index over string or binary columns that accelerates substring search via `contains(col, 'needle')`.
- `RTREE`: R-tree over GeoArrow geometry columns that accelerates spatial filters such as `ST_Intersects` and `ST_Within`.

<Tip title="Working with scalar indices">
Use scalar indexes with:

- Vector search (prefilter results using metadata)
- Full-text search (combining keyword matching with structured filters) 
- SQL scans (optimizing WHERE clauses on scalar columns)
- Key-value lookups (enabling rapid primary key-based retrievals)
</Tip>

## Choosing the Right Index Type

| Data Type                                                       | Filter                                    | Index Type   |
|:----------------------------------------------------------------|:------------------------------------------|:-------------|
| Numeric, String, Temporal                                       | `<`, `=`, `>`, `in`, `between`, `is null` | `BTREE`      |
| Boolean, numbers or strings with fewer than 1,000 unique values | `<`, `=`, `>`, `in`, `between`, `is null` | `BITMAP`     |
| List of low cardinality of numbers or strings                   | `array_has_any`, `array_has_all`          | `LABEL_LIST` |
| String or binary (`Utf8`, `LargeUtf8`, `Binary`, `LargeBinary`) | `contains(col, 'needle')`                 | `FM`         |
| GeoArrow geometry (`geoarrow.point`, `geoarrow.polygon`, `geoarrow.wkb`, ...) | `ST_Intersects`, `ST_Within`, `ST_Contains` and other spatial relationships, `is null` | `RTREE` |

`wait_for_index(...)` waits until the named scalar indexes exist and `index_stats(...)` reports `num_unindexed_rows == 0`. If a table is receiving steady writes, that fully indexed state may not stabilize before the timeout. In LanceDB Enterprise, rows added after the index was built are indexed only once enough have accumulated, so a small remainder can also keep the wait from finishing.

### 3. Update the Index

Updating the table data (adding, deleting, or modifying records) requires that you also update the scalar index. In the embedded library, call `optimize`, which will trigger an update to the existing scalar index.

<CodeGroup>

<Note title="LanceDB Enterprise">
New data added after creating the scalar index will still appear in search results if optimize is not used, but with increased latency due to a flat search on the unindexed portion. LanceDB Enterprise does not support `optimize()`; instead it adds new rows to `BTREE`, `BITMAP` and `LABEL_LIST` indexes in the background once enough have accumulated. It does not update `FM` indexes automatically.

## Indexing nested fields

Scalar indexes can target a scalar field inside a struct by passing its full dotted path. The path is preserved end to end: it's the value you pass to `create_scalar_index`, it's what `list_indices()` reports under `columns`, and it's the column reference you use in filter predicates.

```python
# Schema: pa.struct([pa.field("user_id", pa.int32())]) stored under the `metadata` column.
table.create_scalar_index("metadata.user_id", name="metadata_user_id_idx")

# The same dotted path works in WHERE clauses.
table.search().where("metadata.user_id = 42").limit(1).to_list()
```

<Note>
Nested paths follow Lance field-path semantics: dot-separate each struct field from root to leaf (for example, `metadata.author.name`). The same convention applies to FTS and vector indexes.
</Note>

## FM-Index for substring search

The `FM` index is a scalar index built over string or binary columns that
accelerates substring lookups expressed as `contains(col, 'needle')`. Unlike the
tokenized [FTS index](/indexing/fts-index), which matches whole words after
tokenization, the FM-Index matches arbitrary substrings of the raw bytes. It
works well for URLs, file paths, identifiers, log lines, or any column where you
search for a fragment rather than a word.

Use the FM-Index when:

- Filters use `contains(col, 'needle')` (substring), not equality or word search.
- The column is `Utf8`, `LargeUtf8`, `Binary`, or `LargeBinary`.
- You want substring matches without paying for tokenization, language analysis,
  or BM25 scoring.

Pick `FTS` instead when you need word-level relevance ranking, phrase queries,
or language-aware tokenization.

### Create an FM-Index

Build an FM-Index with the async `create_index` API by passing the `Fm` config in
Python or `Index.fm()` in TypeScript. In Rust, use `Index::Fm(FmIndexBuilder::default())`.
A deployment builds FM-Indexes too, but does not add new rows to them in the background as it
does for the other scalar indexes.

<CodeGroup>
```python Python icon="python"
from lancedb.index import Fm

await tbl.create_index("text", config=Fm())
```

```typescript TypeScript icon="square-js"
import * as lancedb from "@lancedb/lancedb";
import { Index } from "@lancedb/lancedb";

await tbl.createIndex("text", { config: Index.fm() });
```

```rust Rust icon="rust"
use lancedb::index::Index;
use lancedb::index::scalar::FmIndexBuilder;

tbl.create_index(&["text"], Index::Fm(FmIndexBuilder::default()))
    .execute()
    .await?;
```
</CodeGroup>

After the index is built, substring filters use it automatically:

```python
table.search().where("contains(text, 'needle')").limit(10).to_pandas()
```

`list_indices()` reports the index type as `"Fm"`.

## R-tree index for geospatial filters {#rtree}

The `RTREE` index is a scalar index over a column of GeoArrow geometries. It
stores the bounding box of every geometry and accelerates spatial filters, on
their own or as the prefilter of a vector search. Use it when queries restrict
results to a region, such as the scenes over an area of interest, the places
inside a city, or the log records along a route.

### Store geometry as GeoArrow {#rtree-geoarrow}

A column holds geometry when its Arrow field carries GeoArrow extension
metadata: `ARROW:extension:name` names the geometry type, such as
`geoarrow.point`, `geoarrow.linestring`, `geoarrow.polygon` or
`geoarrow.multipolygon` for native coordinates, or `geoarrow.wkb` for
well-known binary. LanceDB keeps that metadata when it stores the column.

You can build the field with PyArrow alone. A point is a struct of `x` and `y`
coordinates:

<CodeGroup>
    <CodeBlock filename="Python" language="Python" icon="python">
    {ScalarIndexRtreeData}
    </CodeBlock>
</CodeGroup>

Libraries such as [`geoarrow-rust-core`](https://pypi.org/project/geoarrow-rust-core/)
(`geoarrow.rust.core`) produce arrays with this metadata already, so a table
built from them works the same way.

### Create an R-tree index {#rtree-create}

Pass the `RTree` config in Python, `Index.rtree()` in TypeScript, or
`Index::RTree` in Rust. The optional page size sets the maximum number of
entries in each R-tree page; it must be at least 2 and defaults to 4096.

<CodeGroup>
    <CodeBlock filename="Python" language="Python" icon="python">
    {ScalarIndexRtreeCreate}
    </CodeBlock>

```typescript TypeScript icon="square-js"

await table.createIndex("location", { config: Index.rtree() });
```

```rust Rust icon="rust"

use lancedb::index::scalar::RTreeIndexBuilder;

table
    .create_index(&["location"], Index::RTree(RTreeIndexBuilder::default()))
    .execute()
    .await?;
```
</CodeGroup>

`list_indices()` reports the index type as `"RTree"`, and `index_stats()`
reports it as `"RTREE"`. In the Rust crate, building the index on a local
table requires the `geo` feature; the Python and TypeScript packages include
it. In the embedded library, `optimize()` adds new rows to the index. Rows
that are not indexed yet are still filtered, just without the index.

### Filter with spatial predicates {#rtree-filter}

Spatial predicates go in `where()` like any other filter. Build constant
geometries with `ST_GeomFromText('<WKT>')` or `ST_Point(x, y)`:

<CodeGroup>
    <CodeBlock filename="Python" language="Python" icon="python">
    {ScalarIndexRtreeFilter}
    </CodeBlock>
</CodeGroup>

The index answers `ST_Intersects`, `ST_Contains`, `ST_Within`, `ST_Touches`,
`ST_Crosses`, `ST_Overlaps`, `ST_Covers` and `ST_CoveredBy` when the indexed
column is the **first** argument and the second argument is a constant
geometry, as well as `IS NULL` on the column. A spatial predicate combined
with other conditions through `AND` still uses the index; one combined through
`OR` with a condition on an unindexed column does not.

The R-tree compares bounding boxes, so it returns a superset of the answer:
every row whose bounding box overlaps the query geometry's bounding box. LanceDB
then evaluates the exact predicate on those candidate rows, so the results are
the same with or without the index. A point just outside a triangle but inside
the triangle's bounding box is read, then discarded.

<Warning>
Write the column as the first argument. With the constant first, as in
`ST_Contains(<constant>, location)`, the index is not used, and the
asymmetric predicates (`ST_Contains`, `ST_Within`, `ST_Covers`,
`ST_CoveredBy`) currently evaluate with their arguments swapped and return
wrong results. This applies to `delete()`, `update()` and `merge_insert()`
conditions as well as queries. Write `ST_Within(location, <constant>)`
instead of `ST_Contains(<constant>, location)`.
</Warning>

Other spatial functions, such as `ST_Distance(location, ST_Point(x, y)) < d`
for a radius filter, work in filters but are evaluated row by row, without the
index. `ST_DWithin` is not available. To use the index for a radius filter,
pair the distance check with an indexed predicate on a bounding polygon:
`ST_Intersects(location, <box>) AND ST_Distance(location, <center>) < d`.

Spatial functions are planar: they treat coordinates as points on a flat
plane, and `ST_Distance` returns a distance in the units of the column's
coordinates. For longitude and latitude, `d` is in degrees, not meters, and a
degree of longitude shrinks toward the poles. Project the data to a metric
coordinate system first if you need distances in meters.

### Combine with vector search {#rtree-vector-search}

A spatial filter on a vector search is a prefilter by default: the R-tree
narrows the candidates first, and the nearest neighbors are found among the
rows that match.

</CodeGroup>

With `prefilter=False` in Python, or `postfilter()` in TypeScript, the filter
is applied to the nearest neighbors instead, without the index, so it can
return fewer rows than the limit.

## Index nested fields

You can build a scalar index on a field inside a struct column by passing the
canonical dot-separated path to `create_index`. This is useful when filters
target attributes nested under a `metadata`-style column, for example
`metadata.user_id` or `metadata.event.type`.

If a literal segment of the path itself contains a dot (for example a column
named `user.id` nested inside `metadata`), wrap that segment in backticks so
LanceDB can tell the dot apart from the path separator: `` metadata.`user.id` ``.

`list_indices()` echoes the same canonical path back, so the column you pass in
round-trips through index metadata regardless of nesting depth or escaping.
