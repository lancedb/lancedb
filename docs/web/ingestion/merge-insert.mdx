Use merge insert when incoming records should be compared with existing rows.
Combine update and insert policies for an **upsert**. Use [append](/ingestion/insert)
when every incoming row should simply be added.

## Merge incoming rows by key {#merge-incoming-rows-by-key}

Merging is different from updating because it involves comparing incoming rows to existing rows by key, and then choosing what to do based on whether the key exists in the target table or not.
Use `merge_insert("id")` in Python or the corresponding SDK builder.

In merge operations, rows are split into three groups:

- **Matched**: key exists in both source and target.
- **Not matched**: key exists only in source.
- **Not matched by source**: key exists only in target.

Conditional merge clauses can compare old and new values. Use the `target.` prefix for the
existing table row and `source.` for the incoming row, for example
`target.last_update < source.last_update`.

Choose a key that identifies the same record in the source and target. Check
for duplicate and null keys before merging. A primary-key declaration does not
enforce uniqueness on ordinary writes, and append operations do not deduplicate
records for you.

A scalar index on the key can help matching. Keep it current and measure the
actual workload rather than assuming every merge uses an index. Enterprise may
reject a merge when the unindexed scan exceeds its configured limit; inspect
that error and the index state before retrying.

## Choose a merge policy {#policies}

| Source and target relationship | Available action |
| --- | --- |
| Key appears in both | Update matching target rows, optionally with a condition. |
| Key appears only in the source | Insert it, or leave it out. |
| Key appears only in the target | Keep it, or explicitly delete it under a synchronization policy. |

### Delete target rows that are missing from source {#delete-target-rows-that-are-missing-from-source}

Use `when_not_matched_by_source_delete()` only when the incoming data is the
complete set for the target scope you intend to synchronize. An incremental
batch is usually not a complete source: deleting everything absent from it
could remove unrelated target records. Inspect the unmatched target keys first.

### Use partial columns in merge updates {#use-partial-columns-in-merge-updates}

Merge updates do not require you to provide values for all columns. You can provide only a subset of columns in source rows. For matched rows, only the provided columns are updated.

Note that in the example above, when `merge_insert` creates a new row, any missing columns are written as `null`. If a missing column is non-nullable in your schema, the insert will fail.

## Check the merged records {#verify}

Inspect the keys that should have changed, confirm that unrelated rows remain,
and check inserted or deleted counts when the SDK returns them. Repeating a
merge is only safe when its keys, conditions and update values produce the
intended result on retry.

### Embeddings and expression predicates {#advanced}

When a table uses an [embedding definition](/embedding), behavior depends on
which source and vector fields the incoming records provide. Do not assume a
partial metadata update recomputes embeddings. Inspect the resulting vector
when changing the input used to generate it.

Rust's `when_matched_update_all_expr` and
`when_not_matched_by_source_delete_expr` accept DataFusion expressions for
LanceDB Embedded tables. Use the string predicate variants for Enterprise tables.
