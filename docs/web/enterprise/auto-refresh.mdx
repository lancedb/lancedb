Both a [computed column](/feature-engineering/add-computed-column) and a
[materialized view](/feature-engineering/materialized-views) can refresh
themselves on a schedule instead of waiting for an explicit
`refresh_column()`, `view.refresh()`, or `REFRESH` statement. Either way,
`auto_refresh_enabled` turns it on and `auto_refresh_interval_seconds` sets
a minimum delay after the last successful refresh before the next
automatic one is eligible -- omit the interval to let the server decide.
See [Architecture](/index#architecture) for the scheduler's place among the
jobs fleet.

## Where the two differ {#granularity}

A computed column's auto-refresh setting is per output: each column
declared in the same `add_columns` call gets its own independent
interval, set when you declare it or changed later. Automatic execution
additionally needs the deployment's `column_refresh.enabled` switch,
which is off in the base configuration.

```sql
ALTER TABLE frames ALTER COLUMN caption SET auto_refresh_enabled = false;
ALTER TABLE frames ALTER COLUMN caption SET auto_refresh_enabled = true;
ALTER TABLE frames ALTER COLUMN caption SET auto_refresh_interval_seconds = 300;
```

A materialized view's setting is whole-view -- there is no per-column
granularity the way a computed column has one setting per output. The
view's *initial* population always happens regardless of this setting;
only the refreshes after that are gated. Unlike a computed column, a view's
setting is declared at `CREATE` time, but it can still be changed
afterward with `ALTER`:

```sql
CREATE MATERIALIZED VIEW my_view AS
SELECT * FROM source_table
WITH (auto_refresh_enabled = true, auto_refresh_interval_seconds = 300);

ALTER MATERIALIZED VIEW my_view SET auto_refresh_enabled = false;
ALTER MATERIALIZED VIEW my_view SET auto_refresh_enabled = true;
ALTER MATERIALIZED VIEW my_view SET auto_refresh_interval_seconds = 300;
```

## Catching up {#catch-up}

Re-enabling a column's auto-refresh after it was off catches up the
entire accumulated backlog in one pass, not just rows written from that
point on -- "catch up," not "resume cadence." Disabling never skips or
drops writes either: rows written while disabled simply commit with no
computed value yet, the same as a row written before the column existed.
