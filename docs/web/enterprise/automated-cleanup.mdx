[Cleanup](/maintenance/cleanup) prunes old table versions and the files only
they referenced. In LanceDB Embedded, that always happens because you asked
for it -- a call to `optimize()`. In LanceDB Enterprise, cleanup can also run
on its own, triggered by the deployment's own maintenance rather than a call
from your application. This page covers how that decision gets made.

## Enabling it {#enabling}

Automatic cleanup is off unless the deployment sets a minimum version age --
with no minimum age configured, nothing is ever old enough to clean up
automatically, and cleanup stays a manual `optimize()` call. A table can also
disable it individually even when the deployment allows it, overriding the
deployment-wide setting for just that table.

## What triggers a run {#triggers}

Once enabled, a table becomes due for cleanup when any one of these is true:

| Trigger | Condition |
| --- | --- |
| Enough new versions | The current version has advanced far enough past the version the last successful cleanup started from |
| Enough time has passed | The last successful cleanup finished long enough ago -- the default is 24 hours -- so an idle table whose versions simply age past the retention window still gets revisited |
| Version went backward | The current version is lower than the version the last successful cleanup recorded, which re-triggers a run immediately |

A table that has never had a successful cleanup run is held to its own
initial version threshold first, so a brand-new table is not claimed for
cleanup before it has accumulated enough versions to be worth the pass.

## Retrying after a failure {#retry}

A failed cleanup attempt is retried, but not immediately -- a minimum delay
(60 seconds by default) must pass after the failure before the table becomes
eligible again. A table with a recent failure and no later success stays
ineligible until that delay elapses, even if one of the triggers above would
otherwise fire.

## Independent of compaction and indexing {#independent}

Cleanup's schedule does not wait on compaction or index-maintenance
decisions for the same table -- it can run in parallel with them. This is
different from how compaction and index maintenance coordinate with each
other; see [Advanced Conflict Resolution](/enterprise/advanced-conflict-resolution)
for why *those* two need to.
